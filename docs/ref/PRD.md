# PRD

PRD는 "무엇을 왜 만들고, 어디까지 만들면 완성인지" 정리하는 문서다.
아래 예시를 보고 `내 프로젝트` 줄을 실제 내용으로 바꾼다.

## Project Name

쉽게 말하면: 만들 것의 이름.

예시:
- 숙제 알림 앱
- 강아지 산책 기록 서비스

내 프로젝트:
- 이름: 문다온 3D 쇼룸 (금강이지스)

## One-Line Summary

쉽게 말하면: 이 프로젝트를 한 문장으로 설명하기.

예시:
- 학생이 숙제를 까먹지 않게 도와주는 앱

내 프로젝트:
- 한 줄 소개: 구현 전에 실제 사용자 결과로 바꾼다.

## Problem

쉽게 말하면: 사용자가 지금 겪는 불편.

예시:
- 숙제를 공책, 단톡방, 머릿속에 따로 기억해서 자주 까먹는다.

내 프로젝트:
- 문제: 사용자가 지금 겪는 핵심 불편을 사용자 언어로 적는다.

## Goal

쉽게 말하면: 만들고 나면 사용자가 할 수 있게 되는 일.

예시:
- 사용자는 해야 할 일을 한곳에서 볼 수 있다.

내 프로젝트:
- 목표: 이번 MVP 또는 기능이 끝나면 가능해져야 하는 결과를 적는다.

## Users

쉽게 말하면: 누가, 언제, 왜 쓰는지.

예시:
- primary: 중학생
- secondary: 학부모
- context: 학교 끝나고 오늘 할 일을 확인할 때

내 프로젝트:
- primary: 첫 사용자 집단
- secondary: 필요 시 보조 사용자 집단
- context: 사용자가 이 제품을 쓰는 상황

## Scope

쉽게 말하면: 이번 버전에 꼭 만들 것. 처음에는 3~5개가 좋다.

예시:
- 기록 추가하기
- 기록 목록 보기
- 완료 체크하기

내 프로젝트:
- 이번 phase에서 실제로 구현할 범위 1
- 이번 phase에서 실제로 구현할 범위 2
- 이번 phase에서 실제로 구현할 범위 3

## Non-Goals

쉽게 말하면: 좋아 보여도 이번에는 일부러 안 만들 것.

예시:
- 결제 기능
- 관리자 페이지
- 친구 초대 기능

내 프로젝트:
- 이번에는 하지 않을 기능 1과 이유
- 이번에는 하지 않을 기능 2와 이유
- 이번에는 하지 않을 기능 3과 이유

## Core Flows

쉽게 말하면: 사용자가 쓰는 순서.

예시:
1. 사용자가 첫 화면을 연다.
2. 시작 버튼을 누른다.
3. 필요한 정보를 입력하고 결과를 확인한다.

내 프로젝트:
1. 사용자가 첫 화면을 연다.
2. 사용자가 핵심 행동을 한다.
3. 시스템이 결과와 완료 상태를 보여준다.

## Functional Requirements

쉽게 말하면: 만들 기능을 표로 정리하기.
중요도는 `꼭 필요`, `있으면 좋음`, `나중에` 중 하나로 적는다.

예시:

| 번호 | 기능 | 중요도 | 설명 |
|---|---|---|---|
| F-001 | 기록 추가 | 꼭 필요 | 사용자가 새 기록을 입력한다 |
| F-002 | 목록 보기 | 꼭 필요 | 저장된 기록을 화면에서 본다 |
| F-003 | 검색 | 있으면 좋음 | 원하는 기록을 찾는다 |

내 프로젝트:

| 번호 | 기능 | 중요도 | 설명 |
|---|---|---|---|
| F-001 | 핵심 기능 1 | 꼭 필요 | 프로젝트가 성립하려면 필요한 기능 |
| F-002 | 핵심 기능 2 | 꼭 필요 | 사용자가 반복해서 쓸 기능 |
| F-003 | 보조 기능 1 | 있으면 좋음 | 없어도 되지만 편해지는 기능 |

## Acceptance Criteria

쉽게 말하면: 이 조건을 만족하면 "완성했다"고 말할 수 있는 기준.

예시:
- [ ] 사용자가 첫 화면을 볼 수 있다.
- [ ] 핵심 기능을 끝까지 사용할 수 있다.
- [ ] 입력한 내용이 저장된다.
- [ ] 잘못 입력하면 안내 문구가 나온다.

내 프로젝트:
- [ ] 핵심 흐름 1개를 끝까지 사용할 수 있다.
- [ ] 필수 입력과 오류 안내가 동작한다.
- [ ] 중요한 데이터가 저장되거나 결과가 유지된다.

## Success Metrics

쉽게 말하면: 잘 만들었다고 판단할 기준.

예시:
- 사용자가 30초 안에 핵심 기능을 사용할 수 있다.
- 첫 화면에서 무엇을 해야 하는지 바로 알 수 있다.
- 오류가 나도 사용자가 다음에 뭘 해야 하는지 알 수 있다.

내 프로젝트:
- 사용자가 핵심 작업 1개를 짧은 시간 안에 완료할 수 있다.
- 첫 화면에서 다음 행동을 바로 알 수 있다.
- 오류가 나도 사용자가 다음에 뭘 해야 하는지 알 수 있다.

## Constraints

쉽게 말하면: 만들 때 지켜야 할 제한.

예시:
- 기능을 너무 많이 넣으면 완성이 늦어진다.
- 사용자가 입력해야 할 것이 너무 많으면 귀찮아질 수 있다.

내 프로젝트:
- technical: 선택한 stack profile에 맞는 초기 구조를 유지한다.
- time: 첫 MVP는 작게 끝낼 수 있는 범위로 제한한다.
- UX: 사용자가 입력해야 하는 정보를 최소화한다.
- operations: 검증 명령과 문서 동기화를 완료 기준에 포함한다.

- 검증이 얕음: Verification Plan을 먼저 적고 실행한다.

## Verification Plan

쉽게 말하면: 진짜 잘 만들어졌는지 확인하는 방법.

예시:
- 첫 화면을 열어본다.
- 핵심 기능을 직접 1번 사용해본다.
- 잘못된 값을 넣었을 때 안내가 나오는지 본다.
- 휴대폰 크기 화면에서도 확인한다.

내 프로젝트:
- automated: `bash scripts/check-project.sh`
- manual: 핵심 사용자 흐름 1개를 처음부터 끝까지 직접 수행한다.
- mobile: 작은 화면에서 글자, 버튼, 입력칸이 잘 보이는지 확인한다.
- error: 잘못된 입력이나 빈 상태에서 안내가 나오는지 확인한다.
